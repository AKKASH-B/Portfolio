04 / Automation

Manual checklist in, living pipeline out.

Every automation effort starts the same way — a requirement, a specification, a list of signals. The work is turning that input into a framework that can execute repeatable tests unattended, catch regressions early, and produce traceable results before they reach the vehicle.

The architecture behind the automation

The framework is built around five distinct layers, separating test execution, verification logic, reusable services, hardware interaction, and reporting. Each layer has a defined responsibility and connects to the next through reusable interfaces.

Layer 01

Application

The layer people actually see — dashboards that pull results together, flag what needs attention, and turn raw logs into something a program manager can read at a glance.

Owns this layer
  • Monitoring
  • Analysis
  • Reporting
Layer 02

Execution

Where test intent becomes a running suite — keyword-driven cases that describe what should happen, structured to scale across ECUs and programs.

Owns this layer
  • Robot Framework
  • Test Suites & Cases
Layer 03

Logic & Verification

Where pass/fail actually gets decided — CAPL drives the logic, with dedicated checks run in both directions and against decoded log data.

Owns this layer
  • CAPL Control
  • Positive / Negative Verification
  • DLT Verification
Layer 04

Services

The tools that talk to the bus and the bench — capturing traffic, taking measurements, and reaching into the test rig itself.

Owns this layer
  • CANalyzer Control
  • Measurement Control
  • MobaXterm Control
Layer 05

Hardware

The real vehicle network everything above exists to validate — ECUs, antenna and displays exchanging signals exactly as they would on the road.

Ground truth
  • ECU
  • TBM Board
  • Antenna
  • Display
  • Speaker
